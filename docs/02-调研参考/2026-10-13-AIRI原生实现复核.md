# AIRI 原生实现复核：收起陪伴、间隔观察、记忆

> 文档状态：调研记录；证明 2026-10-13 在 `aimy-app/`（AIRI v0.12.0-beta.5 副本）内的静态源码观察结果。
> 用途：回答用户「看下airi是怎么做的」，为三项已决定的产品行为提供上游现状依据。
> 边界：本轮只读源码，没有改动、没有运行产品、没有调用模型或设备。

复核对象：本仓 `aimy-app/`，即 AIRI v0.12.0-beta.5 完整副本（R1 落库，提交 `bf41903`）。

## 1. 收起聊天后继续陪伴 — 上游已经是这个语义

**结论：不需要改。** 用户选择的行为就是 AIRI 原版的默认行为。

`apps/stage-tamagotchi/src/main/windows/main/index.ts:155` 起：

```ts
window.on('close', (event) => {
  if (allowClose) { return }
  event.preventDefault()
  window.hide()
})
window.setVisibleOnAllWorkspaces(true)
if (isMacOS) { window.setFullScreenable(false); window.setWindowButtonVisibility(false) }
setWindowAlwaysOnTop(window, true)
```

含义逐条对应：

| 用户要求 | 上游实现 |
|---|---|
| 她是继续在桌面上待着 | 关闭被拦截为 `hide()`，进程不退出 |
| 我能看见她 | `setVisibleOnAllWorkspaces(true)`，切换桌面空间仍可见 |
| 一直看得见 | `setWindowAlwaysOnTop(window, true)` 置顶 |
| 不像一个普通窗口 | macOS 下隐藏窗口按钮、禁全屏 |

注意 `allowClose` 是唯一出口，只有真正的退出路径才放行。R1 已记录的决定「收起聊天 = 桌面角色继续陪伴（沿用原版折叠语义）」与这份源码一致，不需要新增代码。

## 2. 间隔观察 — 机器齐全，但界面只在开发者工具里

**结论：拍摄/推理/发布链条可以直接复用；需要做的是把入口从 `/devtools/vision` 搬到产品界面。**

### 2.1 心跳在 `processing-store`

`packages/stage-ui/src/stores/modules/vision/processing-store.ts`：

```ts
const DEFAULT_CAPTURE_INTERVAL_MS = 3000
const HISTORY_MAX_AGE_MS = 5 * 60 * 1000
const PROCESSING_HISTORY_LIMIT = 240
```

`runTick()` 的三条关键行为：

1. 没有注册处理器直接返回，不会空转拍照。
2. `isProcessing` 为真时只累加 `skippedTicks` 并返回——**上一次推理没结束就不开新的一拍**，天然防叠。
3. 间隔是响应式的：`captureIntervalMs` 用 `useLocalStorageManualReset` 持久化，改动后 `watch` 立即 `clearInterval` 再 `setInterval` 重新上膛，不用重启。

`startTicker()` 先跑一次 `runTick()` 再挂定时器，所以打开即有第一帧，不必等 3 秒。

### 2.2 结果覆盖而不是追加

`packages/stage-ui/src/stores/modules/vision/orchestrator.ts`：发布用 `ContextUpdateStrategy.ReplaceSelf`，`contextId` 为 `vision:${workloadId}:${sourceId}`（无 source 时 `vision:${workloadId}`）。

含义：新一眼**替换**上一次的屏幕上下文，不会在上下文里堆叠 240 条历史把 token 撑爆。历史数组只留在本地 `PROCESSING_HISTORY_LIMIT` 条的环形记录里，不进模型上下文。

### 2.3 并发与成本控制

- `packages/stage-ui/src/composables/vision/vision-read-queue.ts`：`VisionReadQueue` 按服务商各持一个 `Semaphore`，同一服务商的读请求排队，不并发轰炸。
- `packages/stage-ui/src/stores/modules/vision/activity.ts`：跨窗口聚合计数，`synced` 同步；源码内有 `// NOTICE:` 说明主窗口动作最长可能等 5 分钟（`libs/pinia/setup-synced.ts` 的 `callTimeout`，参考上游 PR #2734）。

这两条是「低费用」的实际抓手：间隔可调 + 同服务商串行 + 覆盖式上下文。

### 2.4 工作负载是预定义的

`packages/stage-ui/src/composables/vision/use-vision-workloads.ts` 定义五个：

```
'screen:interpret' | 'screen:understand' | 'screen:ocr' | 'screen:ui-automation' | 'tool:image'
```

各自带提示词模板。间隔观察只需要 `screen:interpret` 或 `screen:understand`，`screen:ui-automation` 属于一期后置的电脑代操作，不启用。

### 2.5 缺口

`apps/stage-tamagotchi/src/renderer/pages/devtools/vision.vue` 是唯一界面，含开始/停止心跳按钮，卸载时 `stopTicker()` 并清理流。产品界面没有任何入口，也没有「她现在正在看」的用户可见反馈。

安全约束在此仍然成立：看屏授权独立、默认关；关闭、隐藏或退出时必须停止采集并拒绝新调用——上游的 `stopTicker()` 加上权限判断可以满足，但需要在搬到产品界面时一并接线。

## 3. 记忆 — 上游没有实现

**结论：这项没有可继承的上游实现，必须自己建。**

证据：

| 位置 | 实际内容 |
|---|---|
| `packages/stage-pages/src/pages/settings/memory/index.vue` | `<WIP />` 占位 |
| `packages/stage-pages/src/pages/settings/memory/modules/memory-long-term.vue` | `<WIP />` 占位 |
| `packages/stage-pages/src/pages/settings/memory/modules/memory-short-term.vue` | `<WIP />` 占位 |
| `packages/memory-pgvector/src/index.ts` | 空壳：`client.onEvent('module:configure', (_event) => {})` 处理器为空，只 `runUntilSignal()` |
| `packages/stage-ui/src/stores/chat.ts` | 只有内存态图片缓存，没有事实记忆接线 |
| `packages/stage-ui/src/database/storage.ts` | IndexedDB 挂载 `airi-local` 与 `airi-sync-queue`，存聊天/会话，**不是**持久事实账本 |

所以「自动存、以后主动提」在 Aimy 里是净新增，不是改配置。这与 R4 手册的定位一致。R4 的 MemoryAdapter / 事实账本设计仍然有效，且必须是自建。

同时确认一个不能动的事实：`storage.ts` 的 `airi-local` / `airi-sync-queue` 命名空间是既有数据契约，R2 §2「明确不改」是正确的。记忆实现要另开自己的命名空间或适配层，不能挤进这两个。

## 4. 更新的通道 — 上游更新检查的完整接线

**结论：决定「先不跟，但预留通道」在代码上代价很低，因为决定更新来源的只有三处，且都在一处文件里。**

### 4.1 三处接线

| # | 位置 | 现值 |
|---|---|---|
| 1 | `electron-builder.config.ts` 三处 `publish` 块（win `:135`、mac `:157`、linux `:252`） | `provider: 'github'`、`owner: 'moeru-ai'`、`repo: 'airi'`、`channel: 'latest-${arch}'`。打包时写进 `app-update.yml` |
| 2 | `auto-updater.ts:39-41` 三条硬编码 URL | `api.github.com/repos/moeru-ai/airi/releases`、`github.com/moeru-ai/airi/releases.atom`、`github.com/moeru-ai/airi/releases/download` |
| 3 | `auto-updater.ts:37` + `:42` | `getReleaseChannelName()` 返回 `latest-arm64` / `latest-x64`；`AIRI_UPDATE_CHANNEL` 环境变量可覆盖通道 |

`publish` 与 `auto-updater` 是配套的：electron-builder 把展开后的 publish 配置写进 `app-update.yml`，electron-updater 读它——这也是源码里那段长 `// NOTICE:` 在解释的事（`${arch}` 必须展开，避免 arm64 读 x64 的元数据）。

### 4.2 当前行为

- `autoUpdater.allowPrerelease = isPrereleaseVersion(app.getVersion())`。当前版本 `0.12.0-beta.5` 是预发布版，所以这个值为**真**。
- `autoUpdater.autoDownload = false`：发现新版本只提示，不自动下载。
- `UPDATE_SERVER_URL` 环境变量是**开发专用**：`auto-updater.ts:88-94` 有 `// NOTICE:` 标明，并且只在 `!app.isPackaged` 时 `forceDevUpdateConfig`。发布版忽略它。
- 缓存目录与日志含 `ai.moeru.airi-updater` 字样（`:64-68`）。

### 4.3 「预留通道」的落地含义

预留不等于现在做迁移。现在要做的只有两件事：

1. **记录触点**：把上面三处登记为「来源切换点」，注明每处的当前值和改动成本。本文即为该记录。
2. **不阻断**：R2 品牌定制时不碰这三处（R2 §2 已列「不改更新检查」）。改名和改图标不会切断更新链路。

真正切换到 Aimy 自有更新源时，改动范围是：三处 `publish` 的 `owner`/`repo`、三条 URL、可选的通道名与缓存目录名。所有改动集中在一个配置文件和 `auto-updater.ts` 顶部的常量区，不涉及业务逻辑。此外发布版首次对外分发前必须处理 `ai.moeru.airi-updater` 字样与 `allowPrerelease` 的取值（自建源上没有预发布通道时，`true` 会让检查落空）。

### 4.4 何时切

按用户决定「先不跟」：本轮不改。切换到自建更新源的触发条件是**开始给受邀用户分发安装包**，而不是现在。当前用户是唯一使用者，更新检查指向上游不会造成实际影响，且能保留一条手动查上游版本的通路。

## 5. 对已决定行为的影响汇总

| 用户决定 | 上游是否已有 | Aimy 需要做的 |
|---|---|---|
| 收起聊天，她留在桌面 | 有 | 无。仅需 R3 验收时实测确认 |
| 记忆自动存、主动提 | 无 | 全部自建（R4 手册范围） |
| 每隔一会儿瞄一下 | 逻辑有，界面无 | 把 ticker 从 `/devtools/vision` 搬到产品界面，接权限门与「正在看」反馈 |
| 先不跟上游、预留通道 | 不适用 | 记录三处切换点，R2 不碰。本文 §4 即为记录 |
