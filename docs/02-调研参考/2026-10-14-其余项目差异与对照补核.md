# 其余项目是否按同一标准分析与测试：补核结果

日期：2026-10-14。状态：源码/离线/同输入补核交付；不是全量应用复现、产品实施或真实效果验收。来源：用户当前要求、固定五项目与AIRI源码、既有功能证据、本轮新增原模块/真实库测试。用途：准确回答“剩下项目是否也验证AIRI缺失/更强”。Chromatic排除。风险：不存在同类接口不等于全仓无能力，局部断言成立不等于用户功能完整或效果优胜。

## 1. 直接结论

**当前五个项目都已按同一判定标准核对，但不能说每个项目所有功能都已同条件测试完，更不能说都比AIRI强。** 前一轮Aions/Ryza/OLV有较多局部正反例，kirara/Charakuru主要沿旧静态/缺陷/结构证据；本轮补齐了后两者更直接的运行与相邻/同输入对照，也纠正AIRI基线的遗漏。

比较单位是一个具体用户能力/契约：AIRI现在已有且真正接线的内容→候选实际实现→同输入或相邻链→正例/拒绝/反例→尚未验证的真实收益。未选入/不适用功能不会为了凑齐计数去安装/启动全服务；这些条目必须保持未测，不伪装成全部完成。

## 3. 记忆基线纠正：AIRI不只有WIP页面

已全文核AIRI `services/computer-use-mcp/src/task-memory/{types,merge,manager}.ts` 与更新/get/clear注册链，新增8项原模块观察（2正向、1拒陈旧、5范围反证）：

- **已有，应先沿用**：结构化更新schema、类型/非空检查、scalar/list合并、精确去重、条数限制、sourceTurnId/轮次水位、done收敛、newTask、MCP更新/读取/清空和上下文格式。
- **仍有具体缺口**：manager仅内存；confirmedFacts是string[]，不是逐事实源消息证明；无本模块持久恢复/CAS/单条纠正删除/词法检索；条数限额不是Token预算。MCP可由LLM提交字段，不等于宿主默认从持久用户消息自动提取。
- **范围反证**：同轮不同payload可补写；clear后旧update可重建；新旧偏好可并存；单条2万字可进入context。它们说明不能原样当长期事实权威，**不声称实际完整service发生用户数据故障**。

因此MEM-F01/02的差异应写“已核默认桌面陪伴链尚未形成持久当前事实/逐条来源/纠正删除/恢复闭环”，不能写“AIRI完全没有memory/来源/陈旧保护”。为用这些纯规则也无需启动一期不开放的电脑操作服务。Minecraft还有内存chatHistory/actions基础，亦登记，不虚构其持久事实能力。

## 4. Kirara补测的实际结果

原Python AST类/方法，真asyncio/线程池；DTO/容器/日志/事件/持久层是显式假边界。AIRI原engine/state/strategy、真Zod和Discord callback实际执行，action/发送为记录器，没有执行终端命令或发信。

| 检验 | 正向结果 | 负例与判定 |
|---|---|---|
| typed Block+Wire | TextBlock→TextConcatBlock沿图传值输出“你好世界”，声明int→str错线拒绝 | 坏运行时返回值仍入结果后失败，条件kwargs错误；未验条件/循环完整正确性、GUI保存恢复 |
| schema/帮助/默认 | Kirara反射元数据；AIRI实际schema/默认/元数据/错bool拒绝均可运行 | 元数据不等于运行值校验，默认bool required标记有反例。不是Kirara独有功能 |
| 可配置组合规则 | prefix/group、禁用、优先级、首命中/无命中工作 | 空group提前True会跳过后续AND。AIRI已有mention/DM/bot gate，不能说无IM/路由 |
| 历史作用域 | Member/Group谓词正反例正确 | query缓存会串extra_identifier；不是更强事实记忆/隔离 |

同输入不等价于公平优胜：AIRI“你好+世界”是原引擎顺序派发，最终拼接来自假action记录器；Kirara是真TextConcat。两种群聊回/不回是不同已配置政策，不能拿回得多作更强。同guild不同channel在当前AIRI Discord共用sessionId仅是该integration合同，不泛化桌面隔离。

**裁决**：KI07的typed图后端、KI06关联的组合规则路由可以记录为“有界差异已验证、一期后置”。它们不因新增而自动变成一期需求。KI04字段schema能力排重/工程参考；KI01继续工程参考。KI03/05/08本轮未补跑，仍有边界，不能称Kirara全部8项都正向测试完。

## 5. Charakuru补测的实际结果

独立Blender5.2.1 factory进程，禁autoexec，不连当前用户场景；只抽取原production.py四函数，输入自建几何/内存空白纹理。piece保留quad/UV，join两组件得2面；restore_uv maxError=0且原顶点不动；半面边界和变拓扑拒绝。**不是完整头身组装/rig/权重/MToon导出**；factory中未启VRM add-on，不据此断言机器没安装。

同一合成GLB在AIRI真实useVRMLoader（现装three-vrm3.5.5）与Kit真实PreviewAvatar中测试，没有fake loader/expression manager/physics：

| 输入/观察 | 两方结果 |
|---|---|
| 无表情/口型/LookAt的最小fixture | 均可加载Humanoid/MToon；均不会自动造出aa/blink/happy或眼动 |
| 人工加有真实morph/骨骼/扩展的同一fixture | 均识别happy/aa/blink、LookAt、Spring；实际happy/aa/blink的morph权重逐项0→1。LookAt仅验证识别，未测实际眼球转向 |
| 同90帧输入、同首顶点采样、物理ON/OFF | 骨角约1.2360521571 rad，顶点位移约0.1158814917，两边相同至浮点误差 |
| Kit原verifySpringMotion多顶点90帧验收 | 最大位移0.2317710024高于其阈值；这是另一测量口径，不与首顶点混成性能分数 |
| 外部纹理URI/计划要求Spring而资产没有 | 原Kit检查拒绝；不发网络 |

最小fixture也故意没有Spring，但Kit标准工艺会制作Spring，不能据fixture断言标准产物无物理。rich fixture是人工加入目标，不是Kit自动生成脸部能力的证据。CPU权重/物理响应不等于真实脸部外观、音素时序、GPU或完整Electron呈现。

AIRI也已有Godot `technical-art-workflow.md`视觉验收流程，要求参考图、同场景前后对照和中间渲染证据。它不等于本次Kit的组件切分、合并、UV恢复等DCC函数实现；这里的差异限于已核导入/运行链之外的这些具体制作工序，不能泛称AIRI没有制作知识或验收流程。

**裁决**：CK01/04从全“待证”收窄为“部分生产/成品检查机制已验证、完整流程与真实产物仍未验”。CK02的VRM导入/已有目标驱动重复，不算新增。正式角色格式仍未选择，未把Kit/Blender/供体或第二renderer搬进产品。

## 6. 当前完成边界与下一步

可以认定：五项目都依据具体功能差异作过核对；对本轮明确列出的关键切片已有原函数/真实库正反例、相邻或同输入对照；本轮补齐了Kirara/Charakuru先前证据不足，并纠正AIRI自身已有能力的遗漏。
