# R4 · 记忆与语音增量技术方案（待批准）

编制日期：2026-10-12。前置：R3 体验评审确认缺口优先级。目标：定义记忆系统与插话能力的架构、数据契约和验收闸门；外部项目只做叶子模块拆解，AIRI 保持唯一会话/音频/权限生命周期。

依据：[GitHub 扩展能力复用调查](../02-调研参考/2026-10-12-GitHub扩展能力复用调查.md)（候选已深读、未安装）、[五项目汇总](../02-调研参考/2026-10-11-五项目复用讨论汇总.md)、PRD 2.0 §3 记忆的产品含义。

## 1. 原则（硬约束）

1. AIRI 的 chat/session/voice/权限/角色生命周期是唯一主链路；外部代码只能成为受约束的 provider、索引、算法或旁路判断器。
2. 记忆的权限、确认状态、纠正、删除、持久化由 Aimy **确定性代码**维护；模型输出的事实不直接写库。
3. 只维护一套事实与来源；索引层（Orama 或 sqlite-vec 二选一）只做召回，不拥有数据。
4. 聊天记录留存 ≠ 记忆；删除记忆 ≠ 删除聊天，但删除后不得因后台提取复活。

## 2. 记忆系统：MemoryAdapter 架构

### 2.1 分层

```
AIRI 会话层（不动）
  └─ context-store 扩展点：每轮请求前注入"记忆候选"
MemoryAdapter（新增，@aimy/memory，放 aimy-app/packages/ 下）
  ├─ 提取（infer）：从用户消息提取事实候选 —— 算法参考 Mem0 OSS
  ├─ 确认（confirm）：自动或用户确认后写入事实账本 —— 待答项
  ├─ 召回（retrieve）：关键词 FTS + 向量 + RRF 融合 —— 参考 MemOS CJK 词法、Hippo rrf.ts
  ├─ 纠正（supersede）：新事实 superseded_by 替代旧事实 —— 参考 Hippo MemoryEntry 契约
  └─ 删除（forget）：确定性多表事务删除 —— Aimy 自管，不用任何候选的 delete
事实账本（SQLite，确定性主表）
  └─ facts 表 + fact_sources 表 + 索引层（Orama 或 sqlite-vec，只做召回）
```

### 2.2 事实账本 schema（初稿，实施前细化）

```sql
facts (
  id TEXT PRIMARY KEY,           -- fact_*
  user_id TEXT NOT NULL,         -- 一期单用户，仍预留
  content TEXT NOT NULL,         -- 事实正文（如"用户喜欢喝温热乌龙茶"）
  kind TEXT NOT NULL,            -- stable（称呼/确认偏好）/ episodic（经历）/ derived（摘要）
  confidence TEXT NOT NULL,      -- confirmed / candidate / rejected
  created_at, superseded_by TEXT REFERENCES facts(id),  -- 纠正链
  source_message_ids JSON        -- 来源消息引用（fact_sources）
)
fact_sources (fact_id, message_id, session_id, created_at)  -- 回到原始消息与时间
```

删除语义（对应 P20-06）：删除一个 fact 时，同事务内处理 facts 行、fact_sources、索引层条目、派生摘要标记失效、异步队列取消；重启后验证不再出现。**Mem0 的 delete 把旧值写 history 的行为明确不采纳**——历史版本仅供查看，不参与召回。

### 2.3 拆解来源与边界

| 来源 | 取什么 | 不取什么 |
|---|---|---|
| Mem0 TS OSS（Apache-2.0） | add/search/update 分层、infer 流程结构 | 云 client、遥测、其 delete/history 语义、其 vector store 作为主表 |
| MemOS local-plugin | `keyword.ts` 的 CJK 清洗/两字短片段 FTS（中文游戏名、昵称召回） | ranker（与 reward 耦合）、宿主、telemetry、未脱敏日志 |
| Hippo | `rrf.ts` 纯函数、source/superseded_by/summary_dirty 契约 | node:sqlite 运行时、整库 |
| AionsHome | 来源追踪、时间检索、压缩策略思想 | Python 进程、其存储/调度及其已知删除竞态 |
| Ryza | 分层/去重/节奏轻量策略 | 音频/宿主/素材 |

### 2.4 接入点

在 `aimy-app/packages/stage-ui/src/stores/chat/context-store.ts` 的上下文装配处注册 MemoryAdapter：每轮请求生成「记忆候选」注入上下文，标记为记忆注入（可追溯）；AIRI 的 Chat Agent、流式、取消逻辑不动。召回快照属于本次请求，不写入跨会话共享状态。

### 2.5 验收闸门（对应调查报告 §七）

- 写入→新会话→新进程召回已确认事实（中文样本：称呼、游戏名、电影名、变化事实）。
- 来源可点开到原始消息；纠正后新事实立即替代，旧事实不再作为现状召回。
- 删除后：检索、派生摘要、生成回答、重启后均不出现；后台提取不复活。
- 用 Promptfoo（MIT，开发期工具不进运行包）固定回归：同一中文数据集跑写入/召回/纠正/删除/重启；关闭遥测。

## 3. 插话自然度：Smart Turn 旁路适配

**问题**（实测 §4）：AIRI 现有 VAD 一过阈值即触发打断，300ms 长度过滤发生在打断之后，防不了短附和/噪声误打断。

**方案**：引入 [smart-turn](https://github.com/pipecat-ai/smart-turn) v3.2 CPU ONNX 模型（BSD-2-Clause），作为 AIRI VAD **旁路判断器**：VAD 触发后不立即打断，而是将最近 8 秒 16k 音频送 Smart Turn 判「用户是否说完」，概率高才执行打断。

- 固定 `smart-turn-v3.2-cpu.onnx` 文件名、模型 revision、预处理（Whisper 特征）与阈值；Python 预处理翻译为 Node/Worker 实现。
- 每次判断绑定 session/turn/generation 标识；旧请求完成不关闭新一轮；接受 AIRI 的 AbortSignal。
- 明确插话识别（VAD 原逻辑）与说完判定（Smart Turn）分工不变更 AIRI 控制权。

**验收**：中文自然停顿不抢话；「嗯」附和不误打断；游戏背景音不误打断；打断发生时停止耗时与 R3-B2 基线持平或更好。

**TEN VAD 不引入**（许可证附加条件 + AIRI 已有 Silero VAD）。ASR/口型先验收 AIRI 现有 Sherpaw/Apple Speech/wLipSync，有真实缺口才进下一轮对照。

## 4. 授权看屏节奏（中期，R3-D4 数据后定案）

沿用 AIRI 现有 `use-vision-screen-capture`，仅补三件事（思路来自 N.E.K.O.，代码重写为 TS）：

1. 截图代次检查：异步返回前校验 generation/source，换源或关闭后丢弃陈旧帧。
2. 响应所有权：观察轮次绑定当前会话请求，不污染下一轮。
3. 采集/理解/开口三频率分离 + token 预算；关闭/隐藏/退出即停，拒绝新调用（Aimy 语义，不照搬 N.E.K.O. 的麦克风联动与遥测）。

低费用模式两方案（间隔看一眼 / 收集变化定时汇总）待 R3-D4 数据后由用户选择。

## 5. 实施顺序建议

1. 记忆契约先行：定义 schema、删除事务、纠正链与测试数据集（不装任何框架）。
2. 召回对照实验：自管小表 + FTS 基线 → 引入 MemOS 词法 → 向量召回（Orama/sqlite-vec 二选一）→ RRF 融合，同一中文数据集对比，选留一层。
3. MemoryAdapter 接入 context-store，走 R3-C2 场景复测。
4. Smart Turn 局部实验（不阻塞记忆线）。
5. 每步单独 commit + Promptfoo 回归 + 手册更新。

每项能力实施前仍按仓库规则先形成对应技术手册与任务边界；本方案是架构依据，不是单次实施授权。
