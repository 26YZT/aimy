## 1. 开发节奏

**快速做出来，一批一批修。**

含义：以可运行、可体验为优先，不追求一次做全。批次之间用真实体验决定下一批内容。这与 R3「实际使用与评审」的定位一致。

## 2. 上游分叉策略

**先不跟，但是预留好更新的通道。**

含义：现在不追随 AIRI 上游的版本演进，但保留将来能拉取上游更新的通道，不把路堵死。

落地代价低，因为决定更新来源的接点只有三处，且集中在一个配置文件与一个文件的常量区。完整接线记录见 [AIRI 原生实现复核](../02-调研参考/2026-10-13-AIRI原生实现复核.md) §4。R2 品牌定制明确不碰这三处。

切换到 Aimy 自有更新源的触发条件是**开始给受邀用户分发安装包**，不是现在。

## 3. 三项产品行为

### 3.1 收起聊天：她继续留在桌面上

**用户原话：「她是继续在桌面上待着，我能看见她。」**

复核结论：**这就是 AIRI 上游的默认行为**，不需要新增代码。`windows/main/index.ts:155` 把关闭拦截为 `hide()`，窗口不退出，同时置顶并跨桌面空间可见。

沿用 2026-10-12 已记录的决定「收起聊天 = 桌面角色继续陪伴」，本次是把「另一种读法」（整个应用最小化后另留小角色）正式排除。

### 3.2 记忆：自动保存，以后主动提

**用户原话：「不用你管，她自己就记住了，以后主动提。」**

含义：

1. 不需要用户确认或手动操作，自动保存。
2. 保存的价值在于**将来主动提起**，不是等用户来检索。

复核结论：**AIRI 上游没有可继承的实现**。设置内三个记忆页面全是 `<WIP />` 占位，`memory-pgvector` 是空壳包，`airi-local` 命名空间只存聊天会话。这项必须自建，范围即 R4 手册。

与既有决定的关系：2026-10-12 已定「记忆验收以『主动提起』为核心指标」。「自动保存」是对另一半问题（保存方式）的作答，两者不冲突。

### 3.3 低费用观察：每隔一会儿瞄一下

**用户原话：「隔一阵看一眼：每隔一会儿瞄一下（看下airi是怎么做的）。」**

含义：间隔式取一帧看一眼，不做连续录制或变化汇总。

复核结论：**推理链条上游已经齐全，但界面只挂在开发者工具里**。`useVisionProcessingStore` 是 `setInterval` 心跳（默认 3000ms），上一拍没跑完就跳过，同服务商串行，结果覆盖式写入上下文。产品界面没有任何入口。

Aimy 需要做的是把入口从 `/devtools/vision` 搬到产品界面，并接上「正在看」的用户可见反馈与看屏权限门。

安全约束不因复用而放松：看屏授权独立且默认关；关闭、隐藏或退出时必须停止采集并拒绝新的调用。

## 5. 立项方法（用户补充）

用户明确的开发顺序，替换此前较松的「按体验补能力」描述：

| 阶段 | 内容 |
|---|---|
| 1 | AIRI 原版成为主工程（**已完成**，R1） |
| 2 | 对用户从 GitHub 找到的较好项目做**拆解复用**：罗列功能清单 → 选择要复用的能力 → 评估是否可复用、是否强于 AIRI 原版能力 → 倒推开发 PRD 或技术手册 → 工程化地把功能加到 Aimy |
| 3 | 基于前面的分析**分阶段开发**，合并前后端 |
| 4 | 再按实际体验迭代 |

对阶段 2 的边界说明：

- 「拆解复用」的产物是**能力清单 + 可复用性评估 + 强于原版的判断 + 倒推的 PRD/技术手册**，不是直接拷代码。
- 每项候选仍须过许可核对（见 [资产清单](../03-技术与协作参考/资产清单.md)）与一期边界（不做游戏代操作、外部消息、支付、云同步、订阅、自建角色）。
- 已有的 [GitHub扩展能力复用调查](../02-调研参考/2026-10-12-GitHub扩展能力复用调查.md)、[Open-LLM-VTuber深度复用评估](../02-调研参考/2026-10-12-Open-LLM-VTuber深度复用评估.md) 属于阶段 2 的输入，按新方法继续补齐「强于原版能力」的对比结论。
- 阶段 2 不阻塞阶段 3 已明确的部分（品牌定制、记忆、观察）。
