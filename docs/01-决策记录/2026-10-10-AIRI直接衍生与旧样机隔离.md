## 1. 旧 Aimy 实际采用了什么方式

旧工程不是全部从零写，也不是直接改造完整 AIRI 应用。准确描述是：**复用 AIRI 的部分包和局部源码，另行组装一个精简桌面应用。**

- `apps/aimy-desktop/src/main/index.ts:13` 明确写着 minimal composition；它建立自己的窗口、配置、会话和媒体服务。
- `apps/aimy-desktop/src/renderer/App.vue:8` 组装自有 AvatarStage、SettingsDrawer、ScreenPicker 和本地会话/语音/观察逻辑，没有沿用原版完整页面与窗口流程。
- `src/preload/index.ts` 建立 `window.aimy` 桥接；虽然同样使用 Eventa，事件、服务与调用流程仍是另一套产品装配。
- `src/renderer/airi-local/database/storage.ts:11` 使用 `aimy-local` 命名空间，原版使用 `airi-local`；相同类型文件不代表状态或数据可以直接共用。
- 当前 `digital-lover/package.json:24` 的默认桌面启动仍指向旧 `aimy-desktop`。原版评估副本在独立的 `.baseline`，还没有成为主产品入口。

因此，界面简化的原因可以确认；真实模型和设备能力的质量仍需实测，不能仅凭外观或旧测试数量判定好坏。旧 UI 与用户想直接继承原版的目标有偏差，不能继续把旧样机称为完整 AIRI 的 Aimy 品牌版本。

## 2. 是否已经冲突，什么情况下会形成难维护的混合工程

当前启动入口、workspace 与评估目录仍分离，未发现两套已在默认产品链路混接。保留两份独立工程本身不会自动产生运行冲突。风险在迁移方式。

本轮对比两边 `apps/*/package.json`、`packages/*/package.json`，发现 **14个同名 AIRI 包**；394个同路径源码文件中，340个字节一致、54个不同。差异可能同时包括上游演进与旧样机定制，不能把54个差异全部认作旧修复或缺陷。范围是两边顶层包的 `src` 文件，不是全仓相似度或代码质量分数。

逐包路径比较见 [结构比较记录](../04-验证记录/AIRI原版评估/2026-10-10-旧样机与原版结构比较.json)。

| 混接风险 | 本地依据 | 处理原则 |
|---|---|---|
| 同名包与锁文件/版本混用 | 14个同名包，部分源码不同；旧workspace具体版本与原版catalog配置不同 | 新主线统一使用固定原版workspace与锁文件，不把两个packages目录覆盖叠加 |
| 两套聊天和音频状态 | 旧自有会话/voice composable，原版chat/session/voice stores | 一个业务只有一套主链路；旧整套装配不迁入 |
| 停止、取消及窗口规则互相打架 | 旧main在minimize时停止媒体，用户希望收起后持续陪伴；原版多窗口有自身生命周期 | 明确每种窗口动作的语义；按原版责任边界作局部修改，不复制旧总控制器 |
| 配置和会话不一致 | 命名空间、密钥存储、账号同步和renderer/main职责不同 | 新产品有明确独立资料目录；数据导入与配置改造另做适配，不共享旧运行目录 |
| 为兼容旧样机不断加分支 | 用同一页面/服务同时支持旧桥接和原版store | 旧样机保留作历史证据，退出新主线默认启动、构建、打包和功能判断 |
| 上游升级难以追踪 | 两份原版快照无可引用commit，且旧包有定制 | 固定来源指纹，补可追溯版本，所有产品增量小步记录；不自动追随上游 |

无法保证未来没有技术债，但可以避免同时维护两套底层实现。**这里采用的是替换主工程基线，旧样机作为参照；不是将两个产品融合为一个。**

## 3. 新 Aimy 的目标

**Aimy 以 AIRI 原版桌面应用作为产品本体，保留原有架构、页面、角色和交互，先完成品牌定制，再按用户体验优化。**

第一版用户打开后应获得原版流程，看到 Aimy 的名称、应用标识和必要品牌界面。先保留已有布局、聊天、设置和人物表现；大范围UI重设计放到真实体验后讨论。后续每项界面调整都基于原版组件与页面进行。

新增记忆、自然插话和主动观察服务于后续优化，不成为先交付这版应用的前置大工程。记忆仍是用户明确的高优先级，但不以先引入记忆框架、重写对话系统为起点。

第一版同样继承原版尚未补齐的能力：改名和改外观不会自动完成长期记忆、自然打断或主动陪伴。已经确认的凭证、电脑工具默认、续聊与退出问题，需作必要的小范围保护或明确待验，不能因“沿用原版”而宣称通过。

## 4. 旧成果如何保留

| 旧成果 | 新主线处理 |
|---|---|
| `apps/aimy-desktop` 的界面、主入口、桥接、会话/媒体装配 | 冻结为历史样机，不整体迁入 |
| 旧拷贝的14个AIRI包 | 以新固定AIRI基线取代；只逐项核对必要补丁，不保留两份运行版本 |
| 取消、陈旧结果、音频队列/解码、日志脱敏、权限与存储保护 | 保留缺陷场景和验证方法；在新基线复现后，按现有接口适配修复 |
| 旧单元/原生测试 | 保留历史证据；有对应新行为时改写适配，不用测试总数推动旧架构迁入 |
| relationship-engine | 后续确有关系规则需要时评估，当前不自动接入 |
| memory、avatar-fitting等占位 | 不迁入来填充目录或代表产品能力 |
| 产品访谈、调研、决策与素材来源记录 | 继续使用；相冲突旧结论明确归档 |

冻结指停止在旧样机扩展产品功能，后续建立可恢复快照并退出主线。当前没有执行物理搬迁、删除、数据迁移或Git重置。

## 5. 接续顺序与验收

| 顺序 | 交付 | 验收重点 |
|---|---|---|
| 1 原版成为主工程 | 从固定AIRI来源建立独立产品工作区，运行原版桌面入口 | 原workspace/锁文件/窗口职责保留；旧样机未进入产品依赖图；来源可追溯 |
| 2 Aimy品牌与必要界面定制 | 名称、图标、窗口/安装标识、品牌文字与必要外观 | 原版交互无回退；资料目录独立；官方服务/更新地址归属明确；保护项有记录 |
| 3 用户实际使用 | 配置可用模型，走文字/图片/语音/角色/窗口流程 | 记录实际成功、延迟、不自然或失败，不先假定必须重写哪个模块 |
| 4 按体验改进 | 优先可靠记忆、自然语音/插话、人物反应，再主动陪伴 | 每次只解决明确缺口，研究复用方案，提供对应回归与体验结果 |

窗口收起、记忆保存和低费用观察的三个选择继续保留待答；它们不阻塞原版继承与初步品牌定制，只约束对应后续行为实现。

“名称/品牌定制”不意味着全局替换所有 `airi` 字符串。内部包名、IPC标识、数据键和协议先沿用原约定；应用名/安装标识、用户资料路径、服务地址与更新源逐项确认，避免搜索替换破坏功能。

## 6. 仓库与来源边界

新主线中的 AIRI 派生源码是 Aimy 实际使用的产品源码，与单独存放的参考仓库不同。仓库中保留实际需要的源码与许可证；参考副本、旧样机运行数据、模板、缓存和凭证不纳入默认产品发布。

建立产品基线先保留原workspace结构，不在同一轮大规模裁剪依赖、改包名和重设计UI。发行范围以桌面应用为目标，其他平台是否从源码仓库裁剪另做核对。

应用可以使用自己的品牌、仓库和迭代路线，上游版权/许可与来源继续保留。人物、SDK、音色等资源另有来源与发行要求，不能由代码改名推断为自有资产。本轮未改Git历史或发布GitHub。
