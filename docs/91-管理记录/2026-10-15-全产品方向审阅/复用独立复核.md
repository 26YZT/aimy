## 判断

**复用边界基本正确，五项目没有遗漏；但目前交付重心明显收窄到“可靠记忆”。首批选记忆符合用户明确选择，不能据此把全产品价值也缩成记忆管理。** Aimy 原目标仍是打游戏、看视频和日常交流时的情感陪伴。记得住只是其中一项必要能力，角色在场、自然语音、当前情境、不打扰和真实相处体验都不能从路线图消失。

本次证据支持“保留首批记忆范围，同时补全产品体验总图与后批回看触发条件”，不支持撤销用户选择、把五个项目全用一遍或立即改实现。

## 8 个具体发现与建议

### F1：首批聚焦正确，但全局顺序缺少核心场景证据（中高关注）

原方向明确“优先陪打游戏、看视频及日常交流”，并要求连续可插话语音、看屏、协调反馈。当前全局分期却把后台续聊排 P2、看屏排 P3、语音/表现排 P4。这是研究推导的顺序，尚没有真实使用证据证明后台续聊比已有语音/看屏体验更急。首批 README 很清楚地限定只是文字记忆批次，不能用它替代总 PRD。

建议：保留已选 MEM-F01/02；在整体路线中单列“原版陪伴场景基线”与后续体验回看。游戏/视频、连续语音、角色反馈的基础体验应早期了解；具体新增优化由实际问题排，不预设全都必须等持久主动之后。这里是评审建议，不授权本轮设备/付费测试。

证据：`docs/00-当前方向/开发方向与边界.md:7-19`；全局 `01-能力选择与分期.md:31-36`；首批 `README.md:11-13`；首批 `06-验收与评测目标.md:87-99`；`docs/PROJECT_STATE.md:31-32`。

### F2：复用优先不等于拿到现成可靠成品（正向确认）

首批已经细化为 Aions 10 个小段、Ryza 2 个小规则，共 4 个源文件；另有 2 项仅参考、4 项拒绝整段移植。AIRI 本身才是直接继承的大块资产；自动事实链的 typed 契约、持久化、取消、UI 与接线大部分仍需适配/补写。当前清单对此诚实，不是从零重做桌面，也不是把两套完整记忆系统接进来。

本次重新计算 4 文件 SHA，全部与交接映射一致；定向重读 Aions 来源白名单/精确主题替换/等待后重查和 Ryza score/select，清单与源代码对应。建议用户沟通继续说“直接沿用 AIRI + 移植已选规则 + 补产品闭环”，不要仅说“复刻”或“拿来即可用”。

证据：首批 `01-复用代码清单.md:7-19,25-49,64-70`；`复用映射.json`；本次 `read-manifest.json`。源码：`AionsHome-main/aion-chat/post_sentinel.py:365-373,391-409,542-558`；`ryza-ai-revive-master/web/js/longterm.js:143-164`。

### F3：最需要早点证伪的是“合适时想起”，而不是再增加存储测试（中高关注）

保存/来源/更新规则能工作，不代表听到含蓄话语时能想到对应记忆。现有离线结果已有同义词漏召回、无关填背景、相对日期并非硬过滤的反例；首批技术方案也承认“生日忘事”“小家伙”是语义待验证点。用户 V2 真正在验的是关联与分寸，含蓄提示比字面命中更难。把词法作为低成本起点合理，把它当成一定能通过 V2 就不合理。

建议：工程契约审定后，在完整 UI 打磨和更复杂后批机制前，先用已批准的同一模型/8 例/总预算做最小可观察链试验，分开看提取、入库、实际送给模型的记忆、最终回应。失败后再选最低成本补救（改提取/关键词与时间路由/候选选择等），不预先增加向量服务，也不靠把期望答案塞入上下文通过。

证据：同条件验证 `2026-10-14-长期记忆召回与主动续聊同条件验证.md:44-59`；首批 `03-技术与数据契约.md:88-94`；首批 `06-验收与评测目标.md:52-67,73-79`；`01-复用代码清单.md:70`。

### F4：OLV 没有被忘记，应该保留条件候选而非为了复用强行纳入（正向确认）

OLV 的主价值不在首批长期记忆：默认 Basic 只是历史，Mem0 适配空，Letta 引出独立服务。译播和点击区域动作确有窄差异，但当前并无已选目标语言/正式 Live2D 资产等前置，所以暂不做合理。它的“系统触发不冒充用户消息”、输出显示/语音/动作职责可继续成为基线合同参考，这不等于增加一个面向用户的功能。

建议：为两个候选写可操作的重开条件和验收要求，保留在产品机会清单。别把“排在后面”写成对整项目价值的否定，也不把工程参考凑进新增能力数。

证据：OLV 后端报告 `2026-10-14-Open-LLM-VTuber后端拆解复用评估.md:54-80,163-178,204-213`；五项目裁决 `105-123`；首批复用清单 `62`。

### F5：Kirara 后置是产品适配正确，不是分析不够（正向确认）

现有补核已经执行 typed 图/组合路由，并记录条件参数/空组/隔离等反例；没有因为技术新颖就纳入桌面单用户陪伴。多人平台路由与自定义工作流不能直接回答“陪我玩游戏是否舒服”。AIRI 已有相邻模块，不能以配置目录搜索不到就宣布产品缺口。

建议：保留两项具体机制，重开条件限定为用户确有外部渠道延续陪伴或可配置行为流程需求；不用“填满候选功能表”推动一期。许可按实际代码使用方式另核，旧报告的绝对化许可判断不应替代具体范围分析。

证据：其余项目补核 `2026-10-14-其余项目差异与对照补核.md:25-46`；全局能力选择 `25,40-44`；旧 Kirara 报告 `372-374`（该处需求边界本身仍合理）。

### F6：Charakuru 的后置合理，但角色体验必须有独立的决策节点（中关注）

正式格式尚未定，Charakuru 是制作侧工具而非 AIRI 运行时能力升级，因此不进入文字记忆实现合理。已有真实库同资产对照说明 AIRI 会消费目标和物理，不需换 renderer；但素材是否有表情、口型、视线和实际外观仍是另一问题。不得用 CPU 物理检查通过替代“角色看起来有感情”。

建议：保留用原版样例完成当前基线，另列后续“具体候选角色 + 音色 + 同场景表现”的审定入口；选定路线才决定是否采用 Charakuru。原报告的“唯一VRM路线”应明确作废，而不是继续悬挂为建议。

证据：其余项目补核 `48-66`；AIRI 清单 `82-90,195-196`；当前方向 `19`；首批 README `39`。

### F7：旧报告仍有会把新模型带偏的有效性冲突（高关注，适合本轮修文档入口）

最新五项目裁决很克制，但旧报告正文仍可被直接检索命中：

- **Charakuru**：`2026-10-13-Charakuru拆解复用评估.md:419,431,442,444` 宣布 VRM 是唯一可行路线、Live2D 不使用、唯一要动手就是制作 VRM。与当前方向 `19`、最新补核 `66` 不相容。
- **Kirara**：`2026-10-13-kirara-ai拆解复用评估.md:336,339-342` 仍写 AIRI 只有配置型 IM、无工作流概念/消息调度/记忆持久化；最新补核 `25-31,39-46` 已具体纠正。“当前桌面缺完整事实链”不能简写成“AIRI没持久化”。
- **OLV 前端**：`2026-10-13-Open-LLM-VTuber前端拆解复用评估.md:653,675,733` 用“领先一个数量级”“全面弱于”等整体强结论；当前五项目裁决 `7,61-65` 明确没有真实体验优胜证明。工程结构可比较，不能据此推体验数量级。

建议：不改原始恢复/机器证据；为旧报告顶部补“哪些结论失效、当前替代入口”的具体标记，必要时把强结论注释为历史判断。最新裁决中已有修正仅放远处还不够，新模型按搜索结果直接读旧报告容易再犯同样错误。这里也是用户说“换模型，要了解一遍”的实际风险。

### F8：当前评测口径正确，但不能拿 8 例或测试数量宣布完整陪伴产品成立（正向确认 + 后续提醒）

最新文档将源码、工程、真实模型、用户试聊分为四层，并明确 8 例不含后台续聊、视觉/声音、正式资产或长期价值；这应保留。已有“24项/17项/20+14项/90帧”均有替身或限定输入，不能相加成产品胜率。五项目统一标准不等于 55 条功能全跑完；不需为了凑覆盖启动不适用的全部候选。

建议：总 PRD 的成功标准应同时保留核心场景、关系体验和稳定使用条件；8 例仅作为首批记忆的决策证据。不要加入尚未通过用户选择的经济/签到/多角色/IM/在线建模来补“产品完整度”。
