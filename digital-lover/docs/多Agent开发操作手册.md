# aimy 多 Agent 开发操作手册

> 目标：让一个人也能用 AI 按大型项目团队的纪律开发，而不是把多个机器人同时扔进同一个文件夹。

## 一、你平时应该在哪里和我说

日常任务继续在当前主对话中告诉我：执行某个阶段、暂停评估新项目、只读检查 AIRI、解释技术手册或开始执行已经批准的任务。当前主对话就是项目总控台，我负责读取项目状态、拆任务、调用子 Agent、整合结果和最终验收。你不需要为每个小任务手动新建窗口。

建议新建独立 Codex 对话的情况：长时间只读调研、独立 UI 视觉探索、外部 GitHub 项目评估、独立代码审查、需要独立工作区写代码，或主对话太长已经混淆产品决策和实现细节。新窗口的作用是隔离上下文，结论必须回写项目文档，不能只留在某个窗口里。

## 二、推荐的最小组织结构

| 角色 | 负责什么 | 是否直接改主工作区 |
|---|---|---:|
| 产品总监 / 主 Agent | 需求、路线、架构、拆任务、整合和最终验收 | 只改已批准任务 |
| AIRI 架构侦察 Agent | 只读检查 AIRI 可复用模块、依赖和边界 | 否 |
| 产品/UX Agent | 用户流程、页面结构、视觉验收条件和原型建议 | 否 |
| 实现 Worker Agent | 一个明确任务的代码实现 | 使用独立分支或 worktree |
| QA/安全审查 Agent | 回归、权限、错误、密钥和测试缺口 | 否 |
| 美术/资产 Agent | VRM、动作、声音和资源验收清单 | 否 |

aimy 当前先使用一个主 Agent 加二至四个临时 Agent，不建立十几个长期机器人。

## 三、需要的软件

必须使用：VS Code、Codex 主对话、Terminal、pnpm、Git、浏览器和 AIRI 只读源码目录。

按阶段使用：Figma 用于正式视觉稿；VRoid Studio 或 Blender 用于角色和 3D 资产；GitHub Issues/Projects 用于任务追踪；Playwright 或 Electron smoke 用于桌面 UI 验证。它们不是同时全部启用，而是任务触发时再使用。

## 四、标准任务流程

### 1. 需求进入主对话

主 Agent 先把自然语言翻译成任务 ID、用户结果、是否改变架构、AIRI 依赖、成功/失败验收和需要用户决定的事项。

### 2. 判断类型

- 问题或调研：只读，输出证据和结论；
- 产品决策：更新 PRD、决策台账或技术手册；
- 实现任务：必须先有批准的技术手册和任务卡；
- 审查任务：只读检查，不顺手修代码；
- 停车任务：先记录想法，不改变当前计划。

### 3. 先写技术手册

必须说明目标、非目标、复用哪些 AIRI 能力、aimy 新增内容、接口、数据流、错误与权限、测试、可见验收和退出条件。

### 4. 用户确认

你确认手册方向后才开始大型实现。没有确认，不直接写产品代码。

### 5. 分派子 Agent

每个子 Agent 必须收到任务 ID、目标、输入文档、允许修改范围、禁止修改范围、验收命令、停止条件和交付格式。

### 6. 实现和审查分离

实现 Agent 不能自己宣布产品完成。主 Agent 或 QA Agent 重新检查 diff、AIRI 复用边界、测试、隐私、错误脱敏、接口兼容和证据。

### 7. 主 Agent 集成

主 Agent 负责合并、冲突处理、补测试和更新 PROJECT_STATE.md。子 Agent 的结论不是最终产品结论。

### 8. 阶段验收

每阶段交付用户说明、技术手册、任务卡、启动命令、测试结果、截图或录屏、已知问题和项目状态更新。

## 五、并行规则

可以并行：AIRI 只读调查、产品流程分析、测试设计、美术资产清单和互不共享接口的独立目录任务。

不可并行：同时修改同一个 store、公共类型或数据库 schema；一个 Agent 改接口、另一个 Agent 同时按旧接口开发；数据模型未冻结就同时开发记忆、关系和 UI；权限边界未确定就同时开发屏幕捕获和主动陪伴。

父仓库目前没有稳定历史提交且存在大量暂存文件。在真正开始并行写代码前，先建立明确基线或独立备份；不自动 reset、清理或覆盖已有暂存内容。

## 六、你中途提出新想法怎么办

直接在当前主对话提出即可。主 Agent 会暂停当前实现，建立候选技术评估任务，只读检查许可证、依赖、接口、维护状态和与 AIRI 的重叠，输出采用、局部借鉴、暂缓或不采用的结论，写入决策台账，等你确认后再改变路线或代码。

## 七、主 Agent 固定恢复提示词

读取 digital-lover/AGENTS.md、docs/PROJECT_STATE.md、当前 PRD、当前阶段技术手册和任务状态。先报告当前阶段、已验证事实、未完成事项、本次唯一任务、允许修改范围和验收命令。如果需求会改变架构、数据模型、权限、公开接口或阶段顺序，先停在设计闸门，不写代码。

## 八、最简单的日常用法

你只要说“继续执行当前已批准任务”“先只读评估这个项目”“给我这一步的技术手册”“暂停，更新产品方向”或“用大白话解释这一步”。我负责决定是否需要新窗口、子 Agent 或设计闸门。你需要管理的是哪些决策已经批准。

## 九、你自己动手试一次（VS Code 现有 Codex 对话即可）

1. 打开 VS Code 当前 aimy 工作区与 Codex 对话，不必另开 VS Code 窗口。
2. 在当前对话发送下面这段话：

~~~text
请在 aimy 项目中并行委派两个只读子 Agent：
Agent A 只检查 AIRI 的 Electron/VRM 能力；
Agent B 只检查 aimy 当前测试和文档缺口。
两人都不得修改任何文件，也不得读取 .env。
等待两人完成后，分别列出证据路径、已确认事实和未确认项，再由你总结。
~~~

3. 观察 Codex 主对话中是否出现子 Agent 活动。当前官方文档说 IDE 扩展在支持后台 Agent 面板时，会在输入框上方出现活动列表；没有面板时以对话中的委派与结果回报为准，不假定每个版本 UI 一样。
4. 要求主 Agent 核对两份报告是否引用不同文件、是否都明确写“未修改文件”；然后再决定下一步。
5. 如果想要严格只读，先检查本轮权限设置；子 Agent 默认继承父线程权限，单靠提示词不是安全边界。不要在含密钥的目录里试跑不受控的外部 Agent。

官方依据：OpenAI 的 Codex Subagents 文档 https://developers.openai.com/codex/subagents 说明了 IDE/CLI 的委派、背景线程、继承权限以及自定义 Agent 文件格式。Agents API 的多 Agent 会话配置是另一条程序化集成路线，不是你现在使用 VS Code 的必备步骤。

## 十、何时手动创建固定 Agent 配置

初期不必创建。等只读委派试跑稳定、需要多次复用相同角色时，才选择将以下文件放在项目根目录的 .codex/agents/，而不是修改 AIRI 参考库或全局配置：

~~~toml
name = "aimy_explorer"
description = "只读调查 AIRI 与 aimy 的复用边界，返回源码路径和风险"
sandbox_mode = "read-only"
developer_instructions = """
只读检查 digital-lover 和 airi-main，不修改任何文件，不读取 .env。
区分已存在、已接入和已验收；输出证据路径、未确认点与建议。
"""
~~~

配置文件名可叫 aimy-explorer.toml；真正识别名称以 name 字段为准。今后也可建立 aimy_reviewer，但先不要配置可写 Worker。官方要求每个自定义 Agent 文件至少有 name、description 和 developer_instructions；项目级目录为 .codex/agents/，用户级目录为 ~/.codex/agents/。目前这只是手册中的示例，**本轮没有替你创建或修改 Codex Agent 配置**。

建议先在单独的试运行对话验证配置是否被当前版本加载，再把它写进常规任务流程。全局 config.toml 的 agents.enabled 默认开启；若当前客户端或供应商不支持，先以实际启动提示为准，不要为了“看见多个机器人”随便升级/切换模型或覆盖你的配置。
