# aimy 既有工作评估报告

> 评估日期：2026-09-29
> 目的：区分可继续复用的资产、需要改造的草稿，以及不应继续沿用的路线。
> 评估依据：digital-lover 当前文件、可运行测试、AIRI 只读源码库。未把聊天中没有文件证据的内容当作完成事实。
> 本轮并行只读 Agent 未完成源码级独立复核；下面的具体分类和测试结论由主 Agent 自行检查仓库与命令，不能冒称为多 Agent 一致性审计。

## 一、结论先说

当前工作不是白做，也不是全部推倒重来。最有价值的成果是：

1. 已经确定了“基于 AIRI 二次开发”的底层方向；
2. 已经把 AIRI Core Agent 的最小依赖闭包接入 aimy 工作区；
3. 已经有一个可测试的 relationship-engine 领域原型；
4. 已经有 text-chat-cli 作为开发期真实模型冒烟工具；
5. 已经形成了隐私、密钥、持久化、测试和阶段闸门等工程约束。

但当前工作还没有形成产品 MVP。Electron、VRM 桌面角色、语音、看屏、主动陪伴、记忆、产品 UI 和安装包都没有被验收。因此，下一步不是继续在现有任务表上盲目往下写，而是用新的 MVP PRD 和阶段手册重新排队。

## 四、当前不继续采用

以下内容不是“代码坏了”，而是与新的开发纪律不匹配：

1. 把 CLI 当作产品架构。CLI 只能验证模型和流式协议，正式产品必须走 AIRI Electron stage 体系。
2. 在没有视觉验收的情况下直接做完整 Electron。先完成 P0/P2 的体验定义和低成本样机，再做桌面壳。
3. 在 aimy 中重新实现 AIRI 的模型连接或 Agent Loop。现有 provider-inference 和 core-agent 应作为唯一底层入口。
4. 先做完整游戏再接入 aimy。游戏是后续独立 vertical slice；MVP 先证明桌面陪伴闭环。
5. 现在实现用户 VRM 导入、云同步、订阅和多角色。这些都会扩大接口和验收面，不能阻塞第一角色闭环。
6. 把接口骨架当成可用功能。companion-engine、memory、avatar-fitting 目前只能标记为接口/占位。
7. 把曾经运行过一次的真实模型对话当成当前永久证据。每次更换 Key、供应商、网络或代码后，都要重新记录冒烟证据。
8. 未经审查地复制 AIRI 整个 monorepo。只按消费边界增量接入，并保持来源、许可证和同步记录。

## 六、重规划后的处理原则

- 旧文件不删除，避免破坏父仓库已有暂存内容和历史证据；
- 新 PRD 和阶段技术手册先作为用户评审草案；用户批准后才成为新的执行依据；
- 每次代码任务先写任务卡，再限定文件范围；
- 任何涉及架构、数据模型、权限、公开接口和费用的变更，先停在设计闸门；
- 每阶段结束更新 PROJECT_STATE.md，并附测试、截图、启动步骤和未解决风险。
